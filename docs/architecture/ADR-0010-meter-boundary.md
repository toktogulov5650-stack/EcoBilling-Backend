# ADR-0010: базовая граница Meter

- Статус: принято
- Дата: 2026-09-25

## Контекст

Счётчик должен быть самостоятельной сущностью, связанной с лицевым счётом. Типы счётчиков, разрядность, пломбирование, жизненный цикл, причины замены и правила показаний пока не утверждены. Добавление этих свойств сейчас зафиксировало бы неподтверждённые бизнес-правила.

## Решение

- `Meter` находится в отдельном модуле Meters.
- Минимальное состояние: `MeterId`, обязательный `AccountId`, `SerialNumber`, `InstalledAt` и `CreatedAt`.
- Серийный номер обязателен и нормализуется как `Trim + ToUpperInvariant`.
- Уникальность серийного номера не вводится до утверждения области уникальности и возможной связи с производителем или типом.
- Уникальность `AccountId` не вводится: один Account может иметь несколько Meters.
- `InstalledAt` и `CreatedAt` приводятся к UTC. Ограничение будущих дат не вводится без отдельного правила.
- Persistence использует schema `meters` и таблицу `meters.meters`.
- Внешний ключ на `accounts.accounts` обязателен и использует `RESTRICT`.
- Минимальный сценарий чтения получает Meter по `MeterId`.
- HTTP endpoints, создание директором, тип, статус, деактивация, замена, пломбы, фотографии и показания не входят в этот этап.

## Последствия

- Базовую модель можно использовать в последующем модуле Readings без преждевременного определения правил показаний.
- Несколько счётчиков могут быть связаны с одним лицевым счётом.
- Существующий Account нельзя удалить, пока на него ссылается Meter.
- История замены в будущем должна добавляться отдельным сценарием без удаления старого Meter.
