# ADR-0014: подтверждённый Payment без провайдерского workflow

- Статус: принято
- Дата: 2026-09-25

## Контекст

Платежи должны быть идемпотентными и связаны с лицевым счётом, но провайдер, callback, проверка подписи, статусы, частичная оплата, переплата, распределение, отмена и возврат пока не утверждены. Модель ожидания или обработки callback без этих решений создала бы небезопасный финансовый workflow.

## Решение

- `Payment` является неизменяемым фактом уже подтверждённой оплаты в модуле Payments.
- Минимальное состояние: `PaymentId`, обязательный `AccountId`, `Amount`, `IdempotencyKey`, `PaidAt` и `CreatedAt`.
- `Amount` должна быть больше нуля и хранится как PostgreSQL `numeric` без фиксированных precision и scale.
- `IdempotencyKey` обязателен, рассматривается как непрозрачная регистрозависимая строка и сохраняется без нормализации.
- `IdempotencyKey` уникален во всём экземпляре EcoBilling одного округа. Повтор ключа запрещён даже для другого Account.
- `PaidAt` и `CreatedAt` приводятся к UTC.
- Внешний ключ на Account обязателен и использует `RESTRICT`.
- Минимальный сценарий чтения получает Payment по `PaymentId`.
- `ProviderReference`, провайдер, callback, подпись, статус, распределение по Charge, изменение баланса, возврат, HTTP endpoints и сценарий записи не входят в этот этап.

## Последствия

- База защищает подтверждённые платежи от повторной регистрации с тем же внутренним idempotency key.
- Отрицательные операции не маскируются под Payment; модель возврата или корректировки должна быть определена отдельно.
- До интеграции с провайдером необходимо определить область уникальности ProviderReference и доверенный способ подтверждения.
- Payment пока не меняет Account и не определяет долг, переплату или распределение по периодам.
