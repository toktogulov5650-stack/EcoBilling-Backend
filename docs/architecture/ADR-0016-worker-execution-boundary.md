# ADR-0016: граница выполнения фоновых заданий Worker

- Статус: принято
- Дата: 2026-09-25

## Контекст

Worker должен запускать долгие, периодические и повторяемые сценарии модулей, но не владеть их бизнес-правилами. Формулы массовых начислений, Outbox, интеграция с платёжным провайдером, расписания и экспорт отчётов пока не определены. Регистрация фиктивного фонового процесса или перенос логики модулей в Worker создали бы ложный контракт и второй источник бизнес-правил.

## Решение

- `EcoBilling.Worker` является отдельной точкой запуска и composition root, которая подключает Infrastructure и сценарии Modules.
- Строка подключения `ConnectionStrings:EcoBilling` обязательна и передаётся в `AddEcoBillingInfrastructure`; секрет не хранится в репозитории.
- Общая граница задания представлена `IWorkerTask`: у задания есть устойчивое имя и асинхронное выполнение с `CancellationToken`.
- `WorkerTaskRunner` выполняет задание с ограниченным числом попыток и фиксированной задержкой из секции `Worker:Execution`.
- Отмена хоста не считается сбоем и не повторяется. После исчерпания попыток исходное исключение передаётся хосту задания, чтобы ошибка не была скрыта.
- Runner пишет структурированные логи и метрики `Meter` с именем `EcoBilling.Worker`: число попыток, повторов, завершений по исходу и полную длительность запуска.
- Идемпотентность и безопасность повторного выполнения являются обязанностью конкретного сценария модуля и его инфраструктурного адаптера. Универсальный runner не может обеспечить бизнес-идемпотентность сам.
- Миграции не применяются автоматически при старте Worker.
- На этом этапе ни одно `IWorkerTask` и ни один hosted service не регистрируются: ещё нет утверждённого фонового бизнес-сценария.

## Последствия

- Появляется единый проверяемый механизм отмены, ограниченных повторов, логирования и метрик без выдуманных бизнес-правил.
- Первый реальный adapter задания должен только вызывать утверждённый handler из Modules и не дублировать его правила.
- Для каждого задания отдельно потребуются решение о расписании или триггере, конкурентности, классификации повторяемых ошибок, идемпотентном ключе и безопасном повторном запуске.
- При появлении нескольких экземпляров Worker потребуется согласовать распределённую координацию и владение заданием.
