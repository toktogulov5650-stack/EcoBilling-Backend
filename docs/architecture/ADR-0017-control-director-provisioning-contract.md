# ADR-0017: внутренний контракт provisioning директора

- Статус: принято
- Дата: 2026-09-26

## Контекст

Первоначального директора экземпляра округа создаёт EcoBilling.Control. Обычная пользовательская авторизация для этого не подходит: системный администратор принадлежит Control, а не EcoBilling. Вызов может быть повторён после timeout, поэтому создание должно быть аутентифицированным, атомарным и идемпотентным без хранения открытой начальной учётной тайны.

## Решение

- Внутренний контракт версионируется как `POST /internal/v1/directors`.
- Endpoint защищён отдельной JWT Bearer scheme и не использует роли локальных пользователей.
- Control подписывает JWT асимметричным RSA-ключом с алгоритмом RS256. Закрытый ключ остаётся только в Control; EcoBilling получает один или несколько публичных ключей.
- JWT обязан содержать известный `kid`, точные `iss` и `aud`, `iat`, `exp`, уникальный `jti` и scope `ecobilling.directors.provision`.
- Максимальная жизнь JWT по умолчанию — две минуты, допустимое расхождение часов — 30 секунд. Оба значения конфигурируются.
- Проверенный `jti` атомарно сохраняется в PostgreSQL до `exp + clock skew`. Повтор одного JWT отклоняется с `service.unauthorized`; повтор операции должен использовать новый JWT.
- Ротация выполняется перекрытием публичных ключей: EcoBilling сначала получает новый `kid`, Control начинает им подписывать, а старый ключ удаляется после окончания жизни ранее выпущенных JWT.
- `Idempotency-Key` обязателен, регистрозависим, сохраняется без нормализации и имеет длину не более 200 символов.
- Канонический fingerprint запроса создаётся HMAC-SHA256 с отдельным серверным ключом длиной не менее 32 случайных байт. Открытая начальная учётная тайна и HMAC-ключ в БД не сохраняются.
- Повтор того же `Idempotency-Key` и того же запроса возвращает исходные `directorId` и `operationId`. Тот же ключ с другим запросом возвращает `operation.idempotency_conflict`.
- Создание `UserAccount`, `DirectorProfile` и `DirectorProvisioningOperation` выполняется в одной PostgreSQL-транзакции. Advisory transaction lock сериализует конкурирующие provisioning-вызовы.
- В одном экземпляре округа допускаются только один `UserAccount` с ролью Director и один связанный `DirectorProfile`. Это защищено частичным уникальным индексом по роли аккаунта, а также уникальным singleton-slot и check constraint профиля.
- Начальная учётная тайна должна быть непробельной строкой длиной от 32 до 256 символов. Она немедленно хешируется стандартным password hasher, не возвращается и не логируется.
- Созданная Identity имеет `RequiresPasswordChange = true`; обычная аутентификация с начальной тайной запрещена и возвращает `auth.password_setup_required`.
- Сценарий безопасной доставки и однократной замены начальной тайны будет опубликован отдельно до пользовательской HTTP-аутентификации. Этот этап не придумывает парольную политику или канал доставки.
- Профиль директора хранится отдельно от `UserAccount` внутри Identity. Полное имя обязательно и очищается только от внешних пробелов.
- Код округа не передаётся и не хранится: весь экземпляр EcoBilling уже принадлежит одному округу.
- Аудит provisioning будет добавлен на этапе 15; Outbox для этого локального синхронного контракта пока не требуется.

## Последствия

- Компрометация публичного ключа одного EcoBilling не позволяет подписывать запросы к другим экземплярам.
- Захваченный JWT нельзя повторно использовать даже в пределах короткого срока жизни.
- Timeout не приводит к созданию второго директора: Control повторяет запрос с тем же `Idempotency-Key`, но новым JWT.
- Для запуска API обязательны строка подключения, issuer, audience, публичные ключи и секрет HMAC-fingerprint.
- Control и EcoBilling должны использовать одинаковые примеры контракта и отдельно тестировать совместимость.
