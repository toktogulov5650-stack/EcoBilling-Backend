# ADR-0019: фундамент наблюдаемости

- Статус: принято
- Дата: 2026-09-28

## Контекст

API уже передавал ограниченный `X-Correlation-Id`, а Worker писал структурированные сообщения и счётчики выполнения. Однако технический `/health` не проверял PostgreSQL, liveness и readiness не различались, телеметрия не экспортировалась, HTTP и PostgreSQL не участвовали в единой распределённой трассе. При этом нельзя допустить попадание паролей, токенов, строк подключения, тел запросов и персональных данных в диагностические сигналы.

## Решение

- API и Worker пишут структурированные JSON-логи в стандартный вывод с UTC-временем и scopes.
- HTTP scope содержит `CorrelationId` и `TraceId`. Итоговое событие запроса содержит метод, шаблон endpoint, status code, длительность, технический идентификатор пользователя и роль, если они доступны после аутентификации.
- Путь с пользовательскими значениями, query string, заголовки, request/response body, токены и учётные данные не журналируются.
- API и Worker регистрируют OpenTelemetry. Ресурс различает сервисы `EcoBilling.Api` и `EcoBilling.Worker`.
- API собирает стандартные HTTP server traces и metrics; оба процесса собирают runtime и исходящие HTTP metrics/traces.
- PostgreSQL traces и metrics подключены через официальный `Npgsql.OpenTelemetry`; sensitive data logging EF Core остаётся выключенным, а безопасное имя пула `EcoBilling` не позволяет строке подключения стать metric label.
- `WorkerTaskRunner` создаёт activity `worker.task.run`, отмечает попытки, retry и итог, а существующие метрики фиксируют попытки, повторы, завершения и длительность.
- OTLP-экспорт логов, traces и metrics включается только при наличии абсолютного HTTP(S) URI в `Observability:OtlpEndpoint`. Без коллектора приложения продолжают работать с локальными JSON-логами.
- `/health/live` проверяет только жизнеспособность процесса.
- `/health/ready` проверяет доступность PostgreSQL. Совместимый endpoint `/health` имеет ту же readiness-семантику.
- Ответ health endpoint содержит только общий статус, имя проверки и длительность; исключения и параметры подключения не раскрываются.
- Успешные вызовы `/health/live` исключены из tracing, чтобы не создавать шум от частых liveness probes. Их HTTP-метрики сохраняются.

## Последствия

- Один trace связывает HTTP-запрос с PostgreSQL и будущими исходящими интеграциями; фоновые задания получают отдельный trace и измеряемый итог.
- Оркестратор может независимо перезапускать неработающий процесс и не направлять трафик в экземпляр без доступной PostgreSQL.
- Включение OTLP не требует изменения кода, но адрес коллектора не является секретом и задаётся окружением как `Observability__OtlpEndpoint`.
- Выбор backend наблюдаемости, sampling, сроки хранения телеметрии, dashboards, alert thresholds и эксплуатационный collector остаются задачей развёртывания.
- Метрика неуспешных входов появится вместе с пользовательским HTTP-сценарием входа; создавать фиктивный auth endpoint или счётчик без события нельзя.
- Health endpoint Worker не открывается отдельным HTTP-сервером до утверждения deployment-модели этапа Docker. Ошибки заданий уже доступны через JSON-логи, metrics и traces.
